SPECIFICATIONS (v2-1) : recettes et ingrédients

Ce fichier ne contient que les nouveautés et les modifications par rapport à la v1 (specs_v1-8). Tout ce qui n'est pas mentionné ici est inchangé.

***** Contexte

Certains aliments d'un repas sont préparés à partir d'une recette : il faut pouvoir décrire les ingrédients qui les composent. Cette version ajoute la notion de type de classe (composante ou combo), la classe Recettes, la liste des ingrédients et leur lien avec les aliments. Elle ajoute aussi l'indication d'utilisation (et un filtre utilisé / non utilisé) dans les listes de l'onglet Admin.

***** Modèle de données

1- types de classe
1-1- chaque classe de repas a un type :
1-1-1- composante : la classe est une composante d'un repas (Protéines, Féculents, Légumes, Laitages, Autres). Elle correspond à une partie de repas, affichée dans l'onglet Repas (comme en v1)
1-1-2- combo : la classe indique seulement qu'un aliment est composé de plusieurs ingrédients. Elle n'a pas de partie de repas et n'est jamais affichée dans l'onglet Repas (ni dans le regroupement des aliments d'un repas, ni dans le popup de génération de repas). Elle est affichée normalement dans l'onglet Admin
1-2- les 5 classes existantes sont de type composante. Une nouvelle classe Recettes, de type combo, est ajoutée (position 6, sans partie de repas)
1-3- un aliment doit avoir au moins une classe de type composante : un aliment qui n'aurait que des classes de type combo est refusé (ajout et modification)
1-4- un aliment qui a la classe Recettes est appelé une recette ; un aliment qui n'a que des classes composante est un aliment simple. Une recette peut aussi avoir d'autres classes (ex. des lasagnes : Protéines, Féculents, Recettes) ; elle remplit alors les parties de repas correspondantes comme en v1
1-5- la règle v1 « sur un aliment utilisé dans des repas, on peut ajouter des classes mais pas en retirer » ne concerne que les classes de type composante (elles changent la composition des repas passés). Ajouter ou retirer la classe Recettes reste possible même si l'aliment est utilisé dans des repas

2- ingrédients
2-1- les ingrédients sont stockés dans une table à part. Un ingrédient n'a qu'un nom (pas de quantité pour l'instant)
2-2- le nom d'un ingrédient est unique, en minuscules, de 1 à 60 caractères. La comparaison est stricte comme pour les aliments ("creme" et "crème" sont deux ingrédients différents)
2-3- chaque aliment est lié à un ou plusieurs ingrédients (table de liaison) :
2-3-1- un aliment simple a exactement 1 ingrédient, qui porte le même nom que lui. Il est créé automatiquement par la base (jamais saisi) ; si un ingrédient de ce nom existe déjà (par exemple créé pour une recette), l'aliment s'y relie sans créer de doublon
2-3-2- une recette a au moins 1 ingrédient, saisis par l'admin. Ces ingrédients peuvent avoir ou non le même nom qu'un aliment existant. Un ingrédient qui n'existe pas encore est créé à la volée à l'enregistrement de la recette ; un ingrédient existant est réutilisé
2-4- quand on renomme un aliment simple, il se relie à l'ingrédient du nouveau nom (créé si besoin). Quand on transforme un aliment simple en recette (ajout de Recettes), ses ingrédients deviennent ceux saisis ; quand on transforme une recette en aliment simple (retrait de Recettes), il se relie à l'ingrédient de même nom que lui
2-5- aucun nettoyage automatique : un ingrédient qui n'est plus lié à aucun aliment reste en base (affiché « non utilisé » dans l'Admin) jusqu'à ce que l'admin le supprime
2-6- règles de gestion d'un ingrédient (onglet Admin, partie Ingrédients) :
2-6-1- ajout : un nom (mis en minuscules). Refusé si le nom existe déjà
2-6-2- renommage : tous les aliments qui l'utilisent suivent (ils pointent vers l'identifiant). Refusé si le nouveau nom existe déjà (pas de fusion). Refusé aussi si l'ingrédient est celui d'un aliment simple (il doit garder le nom de son aliment : il faut renommer l'aliment)
2-6-3- suppression avec confirmation. Bloquée si l'ingrédient est lié à au moins un aliment (aliment simple ou recette), avec un message qui indique le nombre d'aliments
2-7- les ingrédients n'ont aucun effet sur l'onglet Repas : rien n'y est affiché à leur sujet (ils serviront plus tard à la liste de courses)

3- utilisation
3-1- un aliment est « utilisé » s'il est présent dans au moins un repas encore en base (les repas passés sont conservés 30 jours, voir v1 1-6). C'est la même règle que le blocage de la suppression
3-2- un ingrédient est « utilisé » s'il est lié à au moins un aliment
3-3- une contrainte est « utilisée » si elle est attribuée à au moins un jour (comme en v1)

4- journal d'audit
4-1- trois nouvelles actions consignées (rôle admin) : ingredient_add, ingredient_update, ingredient_delete (15 actions au total). Cible : le nom de l'ingrédient ; avant / après : le nom
4-2- pour une recette, l'état avant / après des actions food_add, food_update et food_delete contient en plus la liste de ses ingrédients ({ name, classes, ingredients }). Pour un aliment simple, il reste { name, classes } (son ingrédient est automatique)
4-3- ne sont pas consignés à part : la création automatique d'un ingrédient (aliment simple, ou ingrédient créé à la volée par une recette)

***** Expérience utilisateur

1- Onglet Repas
1-1- les classes de type combo ne sont jamais affichées : un aliment qui a plusieurs classes n'affiche que ses classes de type composante ("sandwich · Protéines, Féculents, Légumes" même s'il est aussi dans Recettes). Les aliments sont regroupés d'après leurs classes composante uniquement
1-2- le popup de génération de repas n'a que les parties de repas des classes de type composante

2- Onglet Admin
2-0- le sélecteur du haut a maintenant trois parties : "Aliments" | "Ingrédients" | "Contraintes"
2-1- partie "Aliments" :
2-1-1- une 6e puce "Recettes" apparaît à côté des 5 autres. Elle affiche les aliments qui ont la classe Recettes
2-1-2- à l'ajout, une case à cocher existe pour chaque classe, Recettes comprise (la classe de la puce affichée est cochée d'office). Pour ajouter un aliment depuis la puce Recettes, il faut cocher en plus au moins une classe de type composante
2-1-3- quand la case Recettes est cochée, un champ "Ingrédients" apparaît (à l'ajout comme dans le popup de modification) : même principe que le champ des aliments du popup de repas (cadres avec croix, liste déroulante filtrée), avec les ingrédients existants en suggestion. Taper un nom qui n'existe pas propose "Créer « nom »" ; Entrée ajoute le nom saisi. Au moins 1 ingrédient est exigé pour une recette
2-1-4- dans la liste, un aliment qui a d'autres classes les indique par des pastilles à droite de son nom (une pastille par classe, ex. "Féculents" "Recettes"). Cela remplace l'indication « aussi : … » écrite sous le nom en v1
2-1-5- sous le nom de chaque aliment : "utilisé dans N repas" ou "non utilisé" (voir 3-1)
2-2- partie "Ingrédients" (même présentation que "Contraintes") : un champ d'ajout, un champ de recherche, puis la liste triée par ordre alphabétique avec, pour chaque ingrédient, son nom, "utilisé par N aliments" ou "non utilisé", un bouton modifier (popup avec le nom) et un bouton supprimer (avec confirmation)
2-3- filtre d'utilisation : dans chaque liste (aliments d'une classe, ingrédients, contraintes), un sélecteur à trois positions "Tous" | "Utilisés" | "Non utilisés" se combine avec la recherche. Pour les aliments, il agit à l'intérieur de la classe sélectionnée. Il revient sur "Tous" quand on change de partie du sélecteur du haut
2-4- l'indication d'utilisation se met à jour quand les repas ou les jours sont modifiés dans l'onglet Repas
2-5- suppression d'un aliment, d'un ingrédient ou d'une contrainte qui est utilisé(e) : comme avant elle est bloquée, mais au lieu d'un simple message elle affiche ce qui l'utilise
2-5-1- une fenêtre « Suppression impossible » indique le nom de l'élément, le message habituel (nombre d'utilisations) et la liste de ce qui l'utilise, avec un bouton « Fermer » :
2-5-1-1- aliment : les repas qui le contiennent, un par ligne ("Mercredi 28 octobre · soir"), du plus récent au plus ancien (midi avant soir)
2-5-1-2- ingrédient : les aliments qui l'utilisent (simples et recettes), triés par ordre alphabétique
2-5-1-3- contrainte : les jours auxquels elle est attribuée, du plus récent au plus ancien
2-5-2- comme la suppression est de toute façon impossible, la fenêtre s'ouvre directement (sans popup de confirmation) quand la liste indique que l'élément est utilisé. S'il n'est pas utilisé, la confirmation habituelle (v1 4-1) s'applique
2-5-3- la liste vient de la base (elle contient aussi les repas de plus de 15 jours qui ne sont plus affichés dans l'onglet Repas, jusqu'à 30 jours dans le passé)

3- Messages d'erreur (nouveaux)
3-1- aliment sans classe de type composante : "Choisissez au moins une classe d'aliment autre que Recettes."
3-2- recette sans ingrédient : "Une recette doit avoir au moins un ingrédient."
3-3- ingrédient qui existe déjà : "Cet ingrédient existe déjà."
3-4- suppression d'un ingrédient utilisé : "Cet ingrédient est utilisé par N aliment(s). Retirez-le de ces aliments avant de le supprimer."
3-5- renommage d'un ingrédient d'aliment simple : "Cet ingrédient est celui d'un aliment simple : renommez plutôt l'aliment."

***** Droits

1- la gestion des ingrédients (liste, ajout, renommage, suppression) est réservée à l'admin, comme celle des aliments. Les rôles read et write n'y ont pas accès

***** Détails techniques

1- migration en deux scripts, à exécuter dans l'ordre sur la base existante :
1-1- 006 : structure (type des classes, classe Recettes, tables des ingrédients, nouvelles fonctions, journal d'audit)
1-2- entre les deux : l'utilisateur ajoute en SQL la classe Recettes aux aliments qui sont des recettes (requête fournie en commentaire de 006 et dans le README). Cela doit se faire avant 007, car depuis l'interface une recette exige au moins 1 ingrédient
1-3- 007 : données. Crée un ingrédient par aliment qui n'est pas une recette et fait le lien. Peut être relancé sans risque (par exemple après avoir ajouté des aliments en SQL)
1-4- ensuite, l'utilisateur ouvre chaque recette dans l'onglet Admin et saisit ses ingrédients. D'ici là une recette sans ingrédient reste un aliment normal dans les repas
1-5- 008 : les suppressions refusées (aliment, ingrédient, contrainte utilisé) renvoient en plus la liste de ce qui les utilise (voir UX 2-5). À exécuter après 007 ; le détail de l'erreur devient du JSON { n, items }, sans changement de signature
2- schema.sql est mis à jour (état final pour une installation neuve). La fausse API du dossier test est mise à jour
3- les fonctions add_food et update_food reçoivent un paramètre supplémentaire (liste des noms d'ingrédients, ignoré pour un aliment simple). Branche de travail : v2
