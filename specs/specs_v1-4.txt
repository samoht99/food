SPECIFICATIONS (v1-4)

***** Contexte général

Un site web qui me permet de définir ma liste de repas pour les jours à venir et la liste des courses correspondante.
Pour la v1 concentrons-nous uniquement sur la partie repas (la liste de courses n'est pas prise en compte pour l'instant).

Aujourd'hui je planifie mes repas pour les 2 prochaines semaines et les écris dans un fichier bloc note, ce qui est pénible.
J'aimerais maintenant que ce soit sur un site web facilement accessible depuis mon pc ou mon smartphone.
Tout le site (interface, messages, libellés) est en français.

***** Expérience utilisateur

1- Ouverture du site
1-1- quand j'ouvre le site web on me demande un identifiant et un mot de passe. Selon l'identifiant (reader, writer ou admin) je suis dans un mode différent et je vois différents onglets
1-2- une fois le site ouvert, je vois une page d'accueil qui affiche les repas d'aujourd'hui et de demain, avec un accès rapide à l'onglet Repas
1-3- un bouton "Quitter" permet de fermer la session pour pouvoir changer de mode

2- Onglet Repas
quand je clique sur l'onglet Repas, je vois la liste des 15 derniers jours, d'aujourd'hui et des 30 prochains jours (aujourd'hui inclus dans la fenêtre). Cette liste est dynamique, chaque jour elle "glisse".
À l'ouverture de l'onglet, la liste défile automatiquement jusqu'à aujourd'hui.
2-1- pour chaque jour on voit les repas correspondant
2-2- pour chaque repas on voit les aliments correspondant à chaque classe
2-3- si un jour est vide = pas de repas rempli, on l'affiche quand même avec ses 2 repas vides
2-4- un repas vide est affiché juste avec la notion "vide"
2-5- un repas rempli est affiché avec ses aliments et à côté la classe de l'aliment. Seules les parties remplies sont affichées (les parties vides ne sont pas affichées)
2-6- je peux modifier un repas = le générer manuellement pour un jour donné en cliquant sur un bouton "Générer repas manuel" situé à côté de chaque repas de chaque jour (le jour et le repas concernés sont donc déjà connus)
2-6-1- un popup d'input apparaît avec les parties du repas à remplir
2-6-2- je peux laisser une partie de repas vide
2-6-3- pour remplir une partie de repas, je ne peux inscrire n'importe quel aliment : l'aliment doit être dans la liste des aliments existant et doit être de la classe correspondant à la partie de repas en question
2-6-4- je peux sélectionner plusieurs aliments pour une même partie de repas
2-7- je peux modifier n'importe quel repas affiché dans l'UI, donc je peux modifier dans le passé les 15 derniers jours et dans le futur les 30 prochains jours.
2-8- un bouton "Vider" à côté de chaque repas rempli permet de supprimer d'un coup tous les aliments du repas (plus simple que de les enlever un par un dans le popup de modification)

3- Onglet Admin
3-1- Il doit permettre les actions suivantes :
3-1-1- afficher la liste de tous les aliments existant, répartis par classe = une liste par classe d'aliments
3-1-2- ajouter un nouvel aliment en lui donnant un nom et l'associant à une classe
3-1-3- modifier un aliment (son nom, sa classe). Tous les repas qui utilisent cet aliment sont modifiés en conséquence (renommer un aliment le renomme partout). Le changement de classe d'un aliment déjà utilisé dans des repas est refusé, car il violerait la règle "une partie de repas ne contient que des aliments de sa classe"
3-1-4- supprimer un aliment avec un popup de confirmation. Si l'aliment est utilisé dans au moins un repas, la suppression est bloquée avec un message qui l'indique
3-2- Il ne doit pas permettre les actions suivantes :
3-2-1- supprimer la liste entière --> devra être fait directement via SQL en DB
3-2-2- supprimer une classe d'aliment --> devra être fait directement via SQL en DB
3-2-3- créer une classe d'aliment --> devra être fait directement via SQL en DB

4- Modifications
4-1- chaque action de suppression doit avoir un popup de confirmation pour être sûr de ce qu'on fait
4-2- chaque action de modification d'un repas déjà rempli doit avoir un popup de confirmation pour être sûr de ce qu'on fait. Cela inclut le fait de vider un repas (via le bouton "Vider" ou en enlevant tous les aliments dans le popup de modification)
4-3- la modification d'un repas vide (génération d'un repas à partir d'un repas vide) ne nécessite pas de popup de confirmation

***** UI

Le site doit être facile d'utilisation et lisible sur ordinateur mais surtout smartphone.

1- Onglet Repas
1-1- le bouton "Générer repas manuel" est à côté de chaque repas dans chaque jour --> en cliquant dessus on sait déjà quel repas de quel jour on modifie
1-2- Concernant le popup de génération de repas :
1-2-1- il affiche chaque partie de repas sur une ligne différente
1-2-2- chaque ligne a la partie de repas à gauche en en-tête et un champ d'input à droite
1-2-3- quand on clique dans le champ d'input, une liste déroulante apparaît avec tous les aliments existant et assignés à la classe correspondant à la partie de repas en question
1-2-4- quand on commence à taper, la liste déroulante affiche seulement les aliments qui contiennent les lettres tapées
1-2-5- quand on sélectionne un aliment, il s'affiche dans le champ d'input, dans un petit cadre avec une croix pour pouvoir l'enlever, et on peut cliquer à côté dans le champ d'input pour ajouter un autre aliment

2- Onglet Admin
2-1- une seule page "Aliments" avec 5 puces (une par classe : Protéines, Féculents, Légumes, Laitages, Fruits) pour passer d'une classe à l'autre sans niveaux de sous-onglets imbriqués. Pour la classe sélectionnée : un champ d'ajout en haut, un champ de recherche, puis la liste triée par ordre alphabétique avec, pour chaque aliment, un bouton modifier et un bouton supprimer.

3- Page de connexion
3-1- elle contient uniquement le titre, le champ identifiant, le champ mot de passe et le bouton "Entrer", sans phrase explicative
3-2- un identifiant ou un mot de passe incorrect donne le même message ("Identifiant ou mot de passe incorrect.") sans préciser lequel des deux est faux

***** Modèle de données

1- repas
1-1- chaque jour comprend 2 repas : le midi et le soir
1-2- un repas est composé de plusieurs parties : une protéine, un féculent, un légume, un laitage, un fruit
1-3- chaque partie dans un repas peut contenir 1 ou plusieurs aliments
1-4- chaque partie de repas correspond à une classe d'aliments
1-5- chaque partie dans un repas ne peut contenir que les aliments de la classe qui lui correspond
1-6- les repas passés (repas d'un jour dans le passé) sont conservés 30 jours en base de données (même si l'UI n'affiche que les 15 derniers jours), puis supprimés automatiquement pour limiter la taille de la base (plan gratuit)

2- classes de repas
2-1- une classe de repas est une catégorie d'aliments
2-2- une classe de repas a donc plusieurs aliments qui peuvent lui être associés
2-3- la correspondance entre classe de repas et partie de repas est la suivante :
2-3-1- classe Protéines = partie protéine
2-3-2- classe Féculents = partie féculent
2-3-3- classe Légumes = partie légume
2-3-4- classe Laitages = partie laitage
2-3-5- classe Fruits = partie fruit

3- liste des aliments existant
3-1- un aliment est défini par son nom et la classe de repas à laquelle il appartient
3-2- un aliment ne peut pas appartenir à plusieurs classes de repas en même temps. Si j'insère un aliment déjà existant mais avec une autre classe je dois avoir une erreur. Insérer un aliment déjà existant dans la même classe donne aussi une erreur.
3-3- la comparaison des noms est stricte : "creme" et "crème" sont deux aliments différents
3-4- casse forcée quel que soit l'input de l'utilisateur :
3-4-1- tout en minuscules pour les aliments, les noms de repas (midi, soir) et les parties de repas
3-4-2- première lettre en majuscule et les autres en minuscules pour les classes
3-5- les aliments sont saisis un par un dans l'onglet Admin (pas d'import initial)

***** Sécurité

1- le site est protégé par 3 utilisateurs (identifiants : reader, writer, admin), chacun avec son propre mot de passe, que l'on entre en ouvrant le site. Selon l'utilisateur je suis dans un mode différent. L'identifiant n'est pas sensible à la casse :
1-1- Read = lecture (identifiant : reader). Grâce à cet utilisateur on a accès au site en lecture, on voit l'onglet "Repas" et son contenu.
1-2- Write = écriture (identifiant : writer). Grâce à cet utilisateur on a tous les droits de l'utilisateur Read + on a accès aux boutons de modification des repas (générer, vider).
1-3- Admin = administrateur (identifiant : admin). Grâce à cet utilisateur on a tous les droits de l'utilisateur Read + on a accès à l'onglet "Admin" avec tout ce qu'il contient et toutes ses actions. Admin ne peut PAS modifier les repas (c'est volontaire) : les actions de modification d'aliments sont réservées à l'onglet Admin, les actions de modification de repas à l'onglet Repas avec l'utilisateur writer.
2- On ne peut pas passer d'un mode à l'autre une fois connecté. Pour changer de mode il faut quitter le site (bouton "Quitter"), le réouvrir pour pouvoir entrer l'identifiant et le mot de passe du mode que l'on veut.
3- Persistance de la session :
3-1- Read et Write : la session est conservée (pas besoin de retaper l'identifiant et le mot de passe à chaque ouverture, par exemple sur smartphone)
3-2- Admin (plus sensible) : le droit est révoqué à chaque fermeture du site / de l'onglet
4- La sécurité est vérifiée côté serveur (base de données), pas seulement dans l'interface : quelqu'un sans le bon identifiant et le bon mot de passe ne peut ni lire ni écrire en contournant le site.
5- Les utilisateurs sont stockés en base dans une table (identifiant, rôle, mot de passe haché) : pour l'instant seulement reader, writer et admin, mais d'autres pourront être ajoutés plus tard directement en SQL.
